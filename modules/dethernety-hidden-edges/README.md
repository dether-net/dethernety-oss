# dethernety-hidden-edges

A backend **`DTModule`** that proposes **inferred attack paths ("hidden edges")**
between a model's components: paths the model does not declare as flows, but
that its exposures, their MITRE ATT&CK techniques and the model's structure
make plausible. It answers one read-only GraphQL query and never writes the
model. A client reviews the candidates; when an operator accepts one, the
client records it as an ordinary data flow of one of the four hidden-edge
classes this module ships.

## What it provides

```graphql
extend type Query {
  """Hidden-edge candidates for a model, as a JSON-encoded string. Read-only."""
  hiddenEdgeCandidates(modelId: ID!, options: String): String
}
```

The returned string is JSON: the answer contract version, the module's
version, the hash of the edge-kind table that produced it, the knowledge-graph
regime, up to 200 **candidates** (kind, the class an accepted edge of that
kind is written with, source and target component, the path techniques, the
exposures that produced it, a tier, the base-field defaults)
and the **counts** of everything the matching left out. A refusal is answered
in the same string, never thrown. The full contract is in
[query-contract.md](../../docs/architecture/dethernety-hidden-edges/query-contract.md).

`options` is a JSON string with at most two keys: `excluded` (candidate ids the
caller has already decided on) and `include_pending` (whether unconfirmed
exposures feed candidates; default `true`).

## The four kinds and their classes

| Kind | Class | What the path is |
|------|-------|------------------|
| `remote-service` | Hidden Edge: Remote Service | A foothold reaches a service over a remote-service or exploitation technique (T1021, T1210) |
| `credential-reuse` | Hidden Edge: Credential Reuse | A credential held at one component is accepted at another (T1078, T1550, T1552, T1555, T1003, T1558) |
| `credential-capture` | Hidden Edge: Credential Capture | A credential crossing a flow is captured next to it and used at its receiver (T1040, T1557) |
| `host-escape` | Hidden Edge: Host Escape | A container breaks out to its host and reaches what runs there (T1611) |

Each class is a data flow class in the category **`Hidden Edge`**. Its id
lives only in its `class.json`: the module reads the four class files once when
it loads, and a missing or malformed file, one outside the `Hidden Edge`
category, or a repeated id fails the load. Its
template holds three base fields (`required_capability`, `required_privilege`,
`granted_privilege`), the fields a reviewing client writes (`hidden_edge_kind`,
`technique_ids`, `source_exposure_ids`, `proposed_by`, `tier`, `rationale`),
and the kind's own fields from the table (`credential_basis`,
`transport_state` and `capture_side`, `escape_vector`).

## What ships

- **`src/`** — the module: the reads, the fold into an in-memory model, the
  matching, the knowledge-graph check, the options parser and the bounds.
- **`src/edge-kinds.json`** — the edge-kind table: 27 rows over the four kinds,
  validated at load (a malformed table fails the module's load). It is
  compiled into the build as `src/edge-kinds.table.ts`, generated by
  `pnpm generate:table`; a test keeps the two equal.
- **`data/dethernety-hidden-edges/dataFlow/<kind>/`** — the four classes:
  `class.json`, `schema.json`, `guide.json`, `tests.json`, the pre-computed
  class embeddings, and `policies.rego`. All four carry **one generic policy**
  (only the Rego package line differs): it turns each well-formed entry of the
  flow's `technique_ids` (at most ten) into one exposure in the category
  **`Inferred Path`**, scored from `granted_privilege`.
- **`class-template/`** — the generic policy and its test cases, which the
  class copies must equal.

The module is a file-policy module (`DtFileOpaModule`): the platform serves
its classes and evaluates their policy as it does for any class module.

## Design notes

- **Read-only by its own discipline.** Every read runs in a read session and a
  read transaction, the runner refuses any Cypher but the module's declared
  reads, and a test refuses write clauses in them.
- **Bounded.** Every read has a cap and one row over it refuses the call as
  `model_too_large`; the module keeps a 25 s deadline below the platform's 30 s
  resolver timeout; each caller has one call in flight.
- **Deterministic.** The same model, table, options and knowledge-graph regime
  give the same answer.
- **Adds no authorization.** The platform's authentication and session scoping
  own access.
- **Known limit: other clients may suggest these classes.** The platform's
  `matchClasses` treats the four classes like any other, so a client's class
  suggestions (by vector similarity, or by name, since "Remote Service" is in
  "Hidden Edge: Remote Service") may offer one for an ordinary flow; the
  platform embeds a class that ships no vector when it installs the module, so
  shipping without embeddings would not prevent it. Each class's description
  says it is never the class of an ordinary flow, and Dethereal's
  `match_classes` drops them.

The design is in
[architecture.md](../../docs/architecture/dethernety-hidden-edges/architecture.md);
what analyses see of an accepted hidden edge is in
[analysis-contract.md](../../docs/architecture/dethernety-hidden-edges/analysis-contract.md).

## Build and test

```bash
pnpm build            # tsc + package (dist/{name}-{version}.tar.gz, with data/)
pnpm test             # hash:check, then vitest
pnpm generate:table   # regenerate src/edge-kinds.table.ts from src/edge-kinds.json
pnpm embed            # recompute the class embeddings
pnpm hash             # recompute the content hash in module.json
```

`pnpm test` first checks the content hash in
`data/dethernety-hidden-edges/module.json` against the class files, then runs
the suite: the table's validation and its lint against the repository (every
technique in the pinned MITRE pack, every anchor and breaker class and
attribute in the open-source catalogue, every emitter locator), the matching
on small positive and negative models per kind, the fold, the reads and their
Cypher lint, the options, the knowledge-graph regime and what it sends, the
classes, and the generic policy run by the platform's own Rego engine against
its `tests.json`. The reads against a real database run in dt-ws's integration
suite.

## Packaging

`manifest.json` declares the module (`compatibility.dtModule: ^0.17.0`). The
package holds the compiled module and its `data/` directory, so the classes
travel with it, and the module ships in the platform release beside
`dethernety-general`, `dethernety-coverage-tools` and
`dethernety-threat-report`.
