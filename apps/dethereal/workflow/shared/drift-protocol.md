## Drift Orchestration Protocol

When resuming {{cmd:threat-model}} on a model that has a drift baseline, run drift detection before computing the step cursor.

1. Resolve the model path (Model Resolution Protocol). Call {{tool:model_state}} with `action: 'get'`.
2. If `baseline_commit` is absent, **skip drift logic** — proceed to step-cursor computation.
3. If the operator asked for a full scan (`--full-scan`), say `[info] Full scan requested; running discovery end-to-end.` and run Step 2 (Discovery) of the `build` phase instead — read the phase's file first, as Phases says, and take up Step 2 whatever the state shows. Drift logic is skipped.
4. Call {{tool:detect_drift}} with the model's `directory_path`. It returns `{ baseline, scoped, renamed, copied, omitted?, truncated?, note? }`: `scoped` is the list of changed files that can affect the model; `renamed` and `copied` are the `{ from, to }` pairs git detected, both paths of each pair in `scoped` (a move not yet staged is a deleted file and a new one, not a pair). On an error (`success: false`), show the operator its `error` text and, from `data`, the refusal code `data.error` and `data.hint`, leave the baseline untouched, and stop drift logic — the operator's next move is what the hint says (e.g., re-run {{cmd:discover}}).
5. If `scoped` is empty **and** there is no `note`, `omitted` or `truncated`, say `[info] No drift since last reconcile (commit <baseline>).` and proceed to the cursor. With a `note`, show it and never report "no drift".
6. If `truncated` or `omitted` is set, say so before anything else: the scan is incomplete, and the files it left out are not re-verified in this pass.
7. Read `<model-path>/.dethereal/discovery.json`. If absent (model created from a description, no discovery run), say `[info] No prior discovery provenance; drift detection skipped. Run discovery to set a baseline.` and proceed to the cursor.
8. Compute `priorElements_in_scope` = elements from `discovery.json` with at least one `sources[].file` in `scoped` (an element whose sources are all outside `scoped` is unaffected by this diff). A `renamed` pair's old path is in `scoped`, so an element whose source was the old path is re-verified against the new one. A source that is a secret file (see Secret files) never counts here: an element whose in-scope sources are all secret files is *not re-verified* — tag it `partial-evidence` — and never REMOVED.
9. Build the file allowlist: `scoped` plus, for each path, the sibling files within one directory level (so the scout can read companion files like `variables.tf` next to `rds.tf`). Then remove from it, after the sibling expansion and again whenever the scout asks for more paths: every secret file in any letter case; every file the name-only search marks as a Secret manifest; every file a compose or kustomization file names as a secret source, in the forms Secret files' wave 1 lists (read the repository's compose and kustomization files, which are not secret, to find them); and every symbolic link or path reached through one (`test -L` on the file, and the physical-path check of Secret files for its directory). A read-only scout cannot recognise a secret file without reading it, so this filter is the guard. Pass the removed secret files to the scout as "present, not read", never their content. Then delegate the re-verification — this is not optional, and it is never done here instead:

   {{#delegate infrastructure-scout-scoped}}Mode: `discover elements`. Model directory: `<model-path>`. File allowlist (read only these paths): <the allowlist, one path per line>. Prior discovery for these files: <the priorElements_in_scope entries>. Return the discovered elements as a JSON array in the discovery output schema, every `sources[].file` taken from the allowlist.{{/delegate}}

10. **Check what came back.** Any returned element with a `sources[].file` outside the allowlist is not evidence: drop that source, and if an element has no source left, drop the element and tell the operator which file the scout cited. Scan the descriptions for credential material and redact (see Relay).
11. Compute the four-way delta locally by joining `priorElements_in_scope` and the returned `newElements` on `suggestedName` (the same key discovery uses):
    - **REMOVED** = a priorElements_in_scope element with no name match in newElements.
    - **ADDED** = a newElements entry with no name match in priorElements_in_scope.
    - **CHANGED-substrate** = name matches in both, but **either** `suggestedComponentType` differs (PROCESS↔STORE↔EXTERNAL_ENTITY transitions are always substrate flips) **or** `suggestedClass.id` differs (or one side has a class while the other doesn't). Substrate flips route through reclassification. *Caveat:* if both sides resolve to the same baseline (`dethernety-general`) class (the thin module case), class-id equality is not proof of substrate equivalence — when the prior element's class is from the baseline (`dethernety-general`) module, force {{tool:match_classes}} against the new file content and use *its* output as the comparison source rather than treating equality as final.
    - **CHANGED-attribute-only** = name matches in both, both `suggestedComponentType` and `suggestedClass.id` are equal (under the caveat above), but the matched element's attribute file content has changed (compare `attributes/<kind>/<id>.json` mtime/content against the matched newElements entry's `sources` evidence).
    - **Partial-evidence flag.** If a matched element's prior `sources[].file` set in `discovery.json` includes paths not present in the extended allowlist (`scoped` + one-directory-level siblings), tag the resulting delta item as `partial-evidence`. The pre-loop summary surfaces the count separately, and per-item prompts append `(partial evidence — out-of-scope sources excluded from re-discovery)` so the operator knows the proposal may be incomplete.
    - **Renamed files.** An element of a renamed file that keeps its name matches as above, and its move is no item (step 16 records it). When its name changed too, the REMOVED item with a source on a `renamed` pair's old path and the ADDED item with a source on its new path each say `(renamed <from> → <to>: may be one element under a new name)`, so the operator can decline both. A `copied` pair is new evidence, not a move: when a returned element has a source on a pair's new path and its matched prior entry has none there, the copy also makes an ADDED item, marked `(copied <from> → <to>: a second instance, or the same element?)` — the add skill's confirm decides.
12. A REMOVED item's model element is the one discovery wrote for it: the element whose name is its `suggestedName` (none, or several: name the item and let the operator say which). It is crown-jewel-tagged when that element's id is mapped in the scope's `crown_jewel_elements` (`.dethereal/scope.json`), or, for a component, when it carries `crownJewel: true` in `structure.json` — so the pre-loop summary can call out crown-jewel-tagged removals.
13. **Drop what is already applied.** A stop mid-loop leaves applied items in the model files while `discovery.json` and the baseline stay as they were, so check each item against the model files before the summary:
    - **REMOVED** whose model element (step 12) no longer exists → applied, drop it.
    - **ADDED** whose `suggestedName` already names an element in `structure.json` or `dataflows.json` → not new: when that element's type or `classData.id` differs from the returned entry's, it becomes a CHANGED-substrate item for that element; otherwise drop it. An item marked `(copied …)` is never dropped here: its name is the original's by design.
    - **CHANGED-attribute-only** whose element is already in `stale_elements` (the `get` of step 1) → queued, drop it.
    - A REMOVED or CHANGED item whose `discovery.json` entry is `confirmed: false` (discovery proposed it; the operator never took it into this model) → no item; step 16 still drops or updates its entry.
    A CHANGED-substrate item applied before a stop is caught at step 15, once its proposed class is known.
14. Emit a one-line pre-loop summary: `[drift] <R> removed (<C> crown-jewel-tagged), <A> added, <S> reclassified, <T> attribute-changed (<P> partial-evidence), <K> secret files changed (not read), <D> already applied since <baseline>.` Suppress the `(<P> partial-evidence)`, `<K> secret files` and `<D> already applied` clauses when zero; after the line, name each REMOVED item step 13 dropped, so an element renamed by hand is not lost unseen.
15. Iterate the delta items. For each:
    - **REMOVED** → say `{{cmd:remove}} <element-id>`. The remove skill's crown-jewel-aware confirm runs for tagged elements; otherwise the generic confirm runs.
    - **ADDED** → say `{{cmd:add}} <suggestedName> (<suggestedComponentType>: <suggestedDescription>)`. The add skill confirms the classification.
    - **CHANGED-substrate** → call {{tool:match_classes}} with the existing element id and the new file content from the relevant `sources[].file` — never a secret file's — and the active `moduleIds` (every module when `activeModules` is absent). When the only fitting class is in a module that is not active, show it as a note — the module and its class — and ask nothing: it is never the proposed class. When the element's `classData.id` already is the proposed class, the item was applied before a stop: say so in one line and ask nothing. Otherwise show the element, its current class, the proposed class, the evidence (file and line), and the partial-evidence note when it applies, then ask:

      {{#ask id=drift-reclassify}}Reclassify <element> from <current class> to <proposed class>? (reclassify / keep){{/ask}}

      Only on `reclassify`: write the new `classData` (`{id, name}`) to `structure.json`, call {{tool:model_state}} with `action: 'stale'`, `add: [<id>]`, and suggest `{{cmd:enrich}} --pick <id>` to refresh attributes against the new class's template.
    - **CHANGED-attribute-only** → call {{tool:model_state}} with `action: 'stale'`, `add: [<id>]` (enrichment takes stale elements first), and suggest `{{cmd:enrich}} --pick <id>`.
    - **A changed secret file** (in `scoped`, removed by the filter) is its own delta item — one per `renamed` pair, not one per path — counted in the summary as `K secret files changed (not read)`. Show the file, its class and the elements that reference it, then ask:

      {{#ask id=drift-secret-file text}}`<file>` changed (not read). Was a credential added, removed or re-scoped? Name the flows or stores it serves, or say "no change".{{/ask}}

      On an answer that names elements, call {{tool:model_state}} with `action: 'stale'`, `add: [<ids>]`, and suggest `{{cmd:enrich}} --focus credentials`. "No change" (a rotated value) resolves the item; only the operator's answer resolves it.
16. **Advance the baseline only after a complete reconcile:** every delta item resolved, **and** the scan was complete (no `truncated`, no `omitted`, no `note`). An item is resolved when it is applied (the element is removed or added), declined by the operator (in the remove or add skill, or with `keep`), queued as stale, or answered at `drift-secret-file`; a suggested command the operator has not run leaves its item open. Then, first, bring `discovery.json` up to date with your edit tool, so the next pass compares against what this one saw:
    - a `sources[].file` or `unreadSecretFiles[].file` on a `renamed` pair's old path takes its new path;
    - a matched element's entry (a CHANGED item, or a match that made no item) takes the returned entry's `suggestedComponentType`, `suggestedClass` and the sources it returned, keeping its sources outside the allowlist and its `confirmed`;
    - an applied REMOVED item's entry is dropped; a declined one stays;
    - an applied ADDED item's returned entry is added with `confirmed: true`; a declined one is not recorded, so it is proposed again when its files change;
    - an item step 13 dropped counts as applied: a REMOVED one's entry is dropped; an ADDED one's returned entry is recorded with `confirmed: true`, also when step 13 turned it into a CHANGED-substrate item; an applied `(copied …)` item is recorded under the name the operator gave it.

    Then call {{tool:model_state}} with `action: 'set_baseline'` and no `commit` — the server records HEAD; on `not_a_git_repo`, `no_commits`, `git_unavailable`, `unsupported_repository` or `git_failure`, leave the baseline where it is, say why, and never retry through a shell. When the reconcile is not complete, leave `discovery.json` and the baseline where they are and say why. Proceed to the cursor.

If the operator stops mid-loop, applied items are durably in the model files, and `discovery.json` and the baseline are unchanged. The next {{cmd:threat-model}} run re-detects the same diff; step 13 drops the items already applied, and an item the operator declined is asked again, since only the baseline advance records it — so is a changed secret file already answered, and an attribute-only change whose stale mark enrichment has since cleared is queued again. Updating `discovery.json` and then the baseline only after a complete reconcile is the whole crash-safety story: a failed `set_baseline` leaves a record the next pass reads correctly.
